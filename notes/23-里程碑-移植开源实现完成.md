## 三、移植期间抓到的 2 个真 bug

### Bug A：`@torch.no_grad()` 把 DgCD 的对抗梯度也禁掉了 ⚠️

`DgCDDomainScorer.update()` 原本用 `@torch.no_grad()` 装饰 —— 但 DgCD 打分内部要对自己的
仿射参数做一次**对抗梯度上升**（Eq.7-8），被 no_grad 包住后 `autograd.grad` 直接报
`element 0 of tensors does not require grad`。

**修法**：`update()` 内显式 `with torch.enable_grad():`（输入已 detach，不影响主干图）。

**为什么之前没暴露**：单域时提前 return 了，压根没进打分分支。多域批量才触发。

### Bug B：每步缓存 12 层激活 ≈ 113 MB，加剧换页 ⚠️

早期版本把每层 (24, 257, 384) 的激活**缓存到 CPU** 等最后统一算，
12 层 ≈ **113 MB/步**；在 16 GB 机器上会明显加剧内存压力。

**修法**：改为 `update()` 里**就地算完分数**，只保留 (层, 通道) 结果（~18 KB），不缓存激活。

## 四、性能实测（本机 Apple M4 / MPS）

| 配置 | 单步耗时 |
|---|---|
| `kl_gauss` 打分，bs=8 | **~2.3 s** |
| `dgcd` 打分，bs=8（手动循环，CPU） | ~3.0 s |
| `dgcd` 打分，bs=8（手动循环，MPS） | ~3.4 s |
| DgCD 打分器单独 | **0.8 ms/层**（12 层 ≈ 10 ms） |

**结论：DgCD 打分本身很便宜**，开销主要在 MPS→CPU 的 12 次张量搬运（每次 ~9.5 MB）。

## 五、⚠️ 环境问题：Docker Desktop 虚拟机抢占整台机器

端到端训练烟测期间出现"**10 分钟只跑 2 步**"，排查结果：

```
PID 7281  472% CPU  2985MB  /System/Library/Frameworks/Virtualization.framework/...  ← Docker Desktop 的 Linux VM
load average: 48 / 35 / 30        （10 核机器，正常应 < 10）
我们的训练进程: 6~7% CPU, 39MB RSS
```

**结论：不是代码问题，是 Docker 的 Linux 虚拟机占了 4~5 个核 + 3 GB 内存。**

同样的代码在 Docker 空闲时跑得很正常（`kl_gauss` 8 步 18.5 s；`dgcd` 4 步 29.1 s）。

**建议**：跑本机训练前退出 Docker Desktop（或至少停掉容器）。
正式训练在 GPU 机器上做，不受此影响。
