> 结论先行：**用官方 DP fork 当底座，但不动它的策略类，而是新增一个我们自己的策略类。**
> 其他候选要么没开源，要么对不上 RoboCasa365，要么太大。

## 二、为什么选官方 DP fork（4 个理由）

### ① 它已经是 RoboCasa365 的官方基线

```
数据管线  : lerobot_dataset.py  → 3 相机 256×256 + 768 维语言 + LeRobot 格式    ✅ 现成
闭环评测  : eval_robocasa.py    → 50 rollouts × task_set，官方协议              ✅ 现成
训练循环  : workspace/...        → 已调通（我们已在 CPU 上跑通）                 ✅ 现成
超参配置  : train_diffusion_transformer_bs192.yaml                             ✅ 现成
```

**这些是"贵但无趣"的部分，全都免费。**

### ② 策略接口只有 5 个方法 → 可以整体替换策略，保留其他一切

从 workspace 源码反推（已核实行号）：

| 接口 | 在哪被调用 | 作用 |
|---|---|---|
| `forward(batch)` → loss | workspace 第 **264** 行 `raw_loss = self.model(batch)` | 训练主损失 |
| `set_normalizer(正常化器)` | workspace 第 **151** 行 | 数据归一化 |
| `get_optimizer(**cfg.optimizer)` | workspace 第 **66** 行 | 优化器参数组 |
| `compute_loss(batch)` | 验证环节 | 验证损失 |
| `predict_action(obs_dict)` → dict | `eval_robocasa.py` | 闭环评测 |

**这意味着：写一个新类实现这 5 个方法，就插进了官方训练/评测管线，且不改官方任何文件。**

### ③ 最小侵入、可回退

- 官方文件**一行不改** → 任何时候都能跑 `train_diffusion_transformer_bs192` 复现基线
- 我们的方法**集中在一个新文件里** → 好维护、好审阅、好开源

### ④ 与排行榜数值直接可比

用官方评测协议跑出来的数字，可以直接和 leaderboard 上 DP 的 15.7 / 0.2 / 1.3 对照。

## 五、需要你拍板的一个设计选择

**动作头：保持 DDPM，还是换成 flow matching？**

| 选项 | 优点 | 缺点 | 我的建议 |
|---|---|---|---|
| **A. 保持 DDPM** | 与官方基线**直接可比**（同一个头，只有编码器不同 → 归因清晰）改动最小 | 头不是最新的 | ★ **L1 用这个** |
| **B. 换 flow matching** | 对齐 CoRP / π0，更"现代" | 同时改了两个因素（编码器 + 头）→ **归因会变模糊** | 作为 **L3 可选项** |

**建议 A**。理由：我们的贡献在**编码器**，L1 必须保证"只有编码器变了"，否则审阅时会问"你的提升是编码器带来的还是换头带来的"。
等 L1 结论扎实了，L3 再换 flow matching 头，证明"与头无关"。

## 六、一句话结论

> **底座 = 官方 DP fork（策略接口只有 5 个方法，我们写个新策略类插进去，官方文件零修改）。**
> **零件从 StarVLA / LingBot 抄**（DINOv2 加载 138 行 + resampler）。
> **动作头 L1 保持 DDPM**（保证归因清晰），L3 再考虑 flow matching。
> 总计约 **1–2 天**工程量，本机 CPU 就能验证形状。
