# 46 - 训练诊断向量化与速度验证

日期：2026-10-20  
对应提交：`f875235`（`v0.12-fast-diagnostics`）

## 1. 慢的根因

慢的不是 4090，也不是 ViT-S/DiT 的 forward/backward，而是每个训练 step
都在执行两套 O(N²) 的 Python pair 循环：

- `mask_iou_by_domain`
- `score_separation_by_domain`

每个 pair 都调用 `.item()` / `float()`，在 N=180 时有：

```
180 × 179 / 2 = 16,110 pair
4 次 IoU + 1 次 score cosine
≈ 8 万次 GPU→CPU 同步
```

另外 `hard_gate.py` 里曾同时存在向量化和旧循环两个同名
`score_separation_by_domain`；后定义的旧循环覆盖了向量化版本，所以只修
`mask_iou_by_domain` 并不能让 step50 的完整诊断变快。

## 2. 代码修复

1. 删除重复的旧 `score_separation_by_domain`，只保留向量化实现。
2. IoU 用矩阵乘法一次算完：
   ```
   inter = keep @ keep.T
   union = s[:,None] + s[None,:] - inter
   ```
   score cosine 同样用 `z @ z.T`；同域/异域聚合也全部在 GPU 上完成，
   最后只做一次 `.tolist()` 回读。
3. 新增 `gate_diagnostics_every`（默认 50）。只有 step 0、50、100… 做完整
   IoU / score cosine / 原型相似度诊断；普通 step 只生成 mask。
4. 非诊断 step 的 IoU / score cosine / 原型相似度沿用上一次诊断值，并显式
   记录 `diagnostics_done` 与 `diagnostics_step`，不再像旧版那样在 step20
   输出一排 0。`layout_resid_frac` / `layout_seen_count` 仍按当前 step 计算，
   但保持为设备标量，只在日志步回读。
5. `_layout_residual` 的逐 layout Python 循环改成 `bincount + index_add`
   一次更新。
6. probe（gate on/off）期间抑制重复诊断，避免 step50 再做一遍 O(N²)。
7. 51 步诊断矩阵默认不保存 checkpoint：
   ```
   checkpoint.save_last_ckpt=false
   checkpoint.topk.k=0
   ```
   旧配置每个 51 步 run 会保存 2 个 1.4GB checkpoint，7 组就会占约 20GB。

## 3. 诊断函数基准（RTX 4090）

脚本：

```bash
python scripts/bench_gate_diagnostics.py --device cuda --sizes 30,60,180 --iters 5
```

“5-call block”= 4 次 IoU + 1 次 score cosine。

| N | 旧 pair loop | 向量化 | 加速 |
|---|---:|---:|---:|
| 30 | 0.2459 s | 0.0022 s | 109× |
| 60 | 0.9748 s | 0.0023 s | 430× |
| 180 | 8.7722 s | 0.0023 s | 3772× |

本地 MPS 上同样验证了数值一致性，N=180 时从 66.2 s 降到 0.013 s。

## 4. 端到端 51 步验证（4090）

命令使用 flow K48、batch 30、drop 33%、layer 11、`gate_diagnostics_every=50`。

从 `GATE_METRICS` 时间戳：

```
step  0 → 20: 13.57 s   （0.68 s/step）
step 20 → 40: 14.11 s   （0.71 s/step）
step 40 → 50:  6.75 s   （0.68 s/step，含 step50 诊断 + gate on/off probe）
```

稳态约 **0.7 s/step**，51 步约 35 秒（不含启动/数据初始化）。
step50 不再出现额外的 2–3 秒诊断尖峰。

step20 日志现在表现为：

```
diagnostics_done=false, diagnostics_step=0
```

表示该行沿用了 step0 的完整诊断，而不是“测出来全是 0”。

## 5. 测试

新增并通过：

- 向量化 IoU / score cosine 与旧 pair loop 的数值等价测试；
- 空 union pair 的语义测试（应被忽略，而不是按 0 计入）；
- `gate_diagnostics_every=2` 的诊断节奏与 carry-forward 测试；
- 本地 `.venv`（MPS）与服务器（CUDA/CPU）均通过
  `scripts/test_hard_gate.py`。

## 6. 服务器磁盘

验证时 `/hy-tmp` 曾 100% 满（50G）。原因是每个 51 步探针都保存了
`latest.ckpt` + topk checkpoint，各约 1.4GB。

已清理：

- `/hy-tmp/runs/mask_matrix/*/checkpoints`（旧版矩阵，已被 fixed 取代）
- `gpu_smoke` / `wrs_smoke` / `speed_bench` 的 checkpoints

保留：所有 `train.log`、`gate_metrics.jsonl`，以及
`flow_k48_51_ckpt`（用于遮挡实验的 checkpoint）。

清理后 `/hy-tmp` 从 100% 降到约 61%（20G 可用）。

## 7. 结论

速度问题已经解决，但科学结论不变：

- 当前 gate 在 51 步探针里仍然没有动作收益；
- WRS 实际采样 mask 的域选择性仍然接近 0；
- DomainDrop 分类头仍然没有学起来。

下一步可以放心用 ~0.7 s/step 的配置继续做机制诊断，而不需要再为避免
每步 10 秒而牺牲诊断频率。
